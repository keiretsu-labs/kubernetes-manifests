# kubelet / Talos node-shell credential surface (2026-10-17)

Read-only documentation audit: where Kubernetes and Talos credentials live on
the nodes and how operators reach them. Derived from the git tree only — no
`kubectl`/`talosctl` write, no live inspection of node filesystems.

## tl;dr

There is **no admin kubeconfig or static token stored on any node image or in
git**. All three clusters keep the same posture:

- the repo kubeconfig (`.kube/config`, tracked, sanitized) lists only operator
  URLs and `token: unused` — identity comes from the tailnet, not a bearer
  token;
- node-level credentials (talosconfig, PKI secrets) are generated by `topf`
  from the SOPS bundle at bootstrap and live **only in `clusterconfig/`
  (gitignored) on the operator workstation and inside the nodes' STATE
  partition** — never committed;
- in-cluster API access for pods rides the Tailscale operator
  (`<location>-k8s` ProxyGroup, `kubeAPIServer.mode: auth`) or plain
  ServiceAccount tokens projected into `/var/run/secrets/kubernetes.io`.

## The three credential layers

### 1. Operator → API: tailnet identity, no static secret

Every documented path to `kubectl` goes through the Tailscale operator
ProxyGroup `<location>-k8s` (`kubernetes/apps/base/tailscale/resources/
proxygroup.yaml`), which serves
`<location>-k8s-operator.keiretsu.ts.net:443` in `auth` mode: the proxy
authenticates the *tailnet identity* of the caller and impersonates it
against the API server. Consequences:

- the tracked kubeconfig can stay credential-free (`token: unused` —
  `architecture.md` "Access itself rides the tailnet");
- **a node holds no operator credential**; a compromised pod cannot replay a
  bearer token to become admin over this path — it would first need tailnet
  identity;
- `tools/kc.sh` is the only sanctioned entrypoint and needs no per-cluster
  secrets on disk beyond tailnet membership.

The `k9s` conveniences in `clusters/talos-*/.mise.toml` reference contexts
`admin@k8s.ottawa.local` / `admin@k8s.stpetersburg.internal`. Those contexts
live in the *workstation* kubeconfig produced by `task kubeconfig`
(`talosctl kubeconfig` → `../../kubeconfig`, `chmod 600`) — an admin-capable
certificate pair fetched from the Talos API, gitignored, never shipped to
nodes.

### 2. Node → API: kubelet client certs, rotated

Each kubelet authenticates with a client certificate; all three clusters set
`rotate-server-certificates: "true"` in `all/<n>-kubelet.yaml` (ottawa 15,
robbinsdale 14, stpetersburg 13) so serving certs rotate via the CSR API, and
Talos rotates the client side internally. No long-lived token or
`--token` flag is configured anywhere in `clusters/talos-*/bootstrap/talos/`
(verified by grep). The kubelet reads its key material from the machine
config rendered into the STATE partition — the same material `topf`
(`mise run genconfig`) renders to `clusterconfig/<host>.yaml`, which is
gitignored per `.gitignore` (`**/talos/clusterconfig/`).

### 3. Pods → API: projected SA tokens only

Workload pods use the standard projected service-account token volume
(`/var/run/secrets/kubernetes.io/serviceaccount`). Nothing in the tree mounts
hostPath `/etc/kubernetes` or copies admin kubeconfigs into pods; the only
custom token-bearing Secrets are app-scoped (`bot-viewer` read-only pair,
`firefly-source`, `ts-*` clients — see `docs/security/` inventories).
`automountServiceAccountToken` is left default; hardening that per-workload is
a separate lane item, not a credential-surface defect.

## Talos API itself

- `talosctl` auths with the talconfig-derived `talosconfig`
  (`clusterconfig/talosconfig`, workstation-only, chmod 600).
- On the nodes, the Talos API (`apid`, port 50000) trusts the cluster CA;
  **the CA + talosconfig secret material originates from
  `talsecret.sops.yaml`** (`secretsPath` in every `topf.yaml`, PGP
  `FAC8E7C3…`, encrypted at rest in git) and is laid down by the machine
  config at install. The only plaintext secrets artifact ever allowed in the
  repo is the `.example` stub.
- `kubernetesTalosAPIAccess` is enabled on all three control-plane patches
  (`control-plane/10-api-access.yaml`) with `allowedRoles: [os:admin]`
  limited to `allowedKubernetesNamespaces: [system-upgrade]` — i.e. pods may
  call the Talos API through kubePrism **only from the
  `system-upgrade` namespace**, and only with the `os:admin` role. That is
  the single sanctioned pod→node-API path (tuppr upgrades); no other
  namespace can reach node shells through it.

## Findings

| # | severity | observation |
|---|---|---|
| C1 | Info | No admin kubeconfig/token is stored on nodes or in git; workstation creds are gitignored `clusterconfig/` + fetched `kubeconfig`. Posture correct. |
| C2 | Info | `kubernetesTalosAPIAccess` pod→Talos bridge is scoped to ns `system-upgrade` + role `os:admin` on all clusters — least-privilege as intended (tuppr only). |
| C3 | Info | kubelet serving certs rotate (`rotate-server-certificates: true` ×3); no static token flags anywhere in bootstrap trees. |
| C4 | Low | `k9s` mise tasks pin contexts `admin@k8s.ottawa.local` / `admin@k8s.stpetersburg.internal`, which exist only in the untracked workstation kubeconfig — cosmetic doc trap, not exposure (robbinsdale has no k9s task). |
| C5 | Info | `talsecret.sops.yaml` is the root of trust for both cluster CAs; single PGP recipient (fleet key). Loss of that key = re-bootstrap; noted in SOPS docs. |

**Verdict: no-finding requiring action.** The credential surface is
tailnet-identity front door + rotated kubelet certs + namespace-scoped Talos
API bridge; nothing to fix in git. C4 recorded as cosmetic.
