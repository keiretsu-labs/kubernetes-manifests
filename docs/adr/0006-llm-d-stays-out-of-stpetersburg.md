# llm-d stays out while St. Petersburg serves a single endpoint

[llm-d](https://github.com/llm-d/llm-d) is a Kubernetes-native distributed inference stack — a CNCF Sandbox project since March 2026, backed by Red Hat, IBM, Google, CoreWeave and NVIDIA — that puts an Endpoint Picker (EPP) above vLLM, SGLang or TensorRT-LLM and routes each request to the replica most likely to already hold its prompt prefix in KV cache. It is well engineered and it is not a fit for St. Petersburg as configured, because every capability it sells is a capability for choosing among replicas, and this cluster serves exactly one.

The arithmetic is the whole decision. St. Petersburg has three arm64 Talos nodes: `orin-0` (control plane, no `nvidia.com/gpu` capacity) and `spark-0` / `spark-1` with one GB10 each — two GPUs in the cluster, total. The served model, `Mia-AiLab/GLM-5.3-Flash-EXL3-TR3-4bpw` at roughly 164 GiB, is a single `LeaderWorkerSet` with `replicas: 1` and `size: 2`: one vLLM tensor-parallel group whose rank 0 is on `spark-0` and rank 1 is on `spark-1`, joined over the RDMA rail. Both GPUs are inside one serving instance, so there is exactly one endpoint to route to. Be precise about what that depends on, because it is easy to state it wrongly: it follows from the **model**, not from the hardware. A checkpoint that fits a single GB10 would run at TP=1 as two independent replicas on the very same two GPUs — no purchase required — and that is the real threshold this decision turns on. Two accelerators are enough for two replicas; they are not enough for prefill/decode disaggregation, which needs separate prefill and decode pools and so at least four. An EPP in front of one endpoint does not schedule anything; it forwards, having first parsed the body to compute a prefix hash whose only purpose is to pick between candidates that do not exist. That is a hop and a failure domain in exchange for nothing.

Nor is llm-d shaped for this deployment even setting replica count aside. Its `guides/recipes/modelserver/base/` tree contains only `single-host` variants (`default`, `pd`, `e-pd`); multi-node tensor parallelism lives in the separate `wide-ep-lws` guide, validated on 32×H200 and 32×B200 clusters. A two-node TP group is not the shape the well-lit paths are cut for at either end of the range. The `optimized-baseline` guide — the one the project tells most users to start from — defaults to Qwen3-32B at **8 replicas × TP=2 = 16 GPUs**. This cluster has two.

The router also does not fit, in the ordinary scheduling sense. Rendering `oci://ghcr.io/llm-d/charts/llm-d-router-standalone:v0.10.0` produces a single Deployment with two containers: an Envoy sidecar requesting 4 CPU / 8 Gi (16 Gi limit) and the endpoint picker requesting 8 CPU / 8 Gi (16 Gi limit) — **12 CPU and 16 Gi of requests in one pod, with 32 Gi of limits**. Against that, the live cluster has `spark-0` at 98% of allocatable memory requested, `spark-1` at 99%, and `orin-0` at 78% of a 5.4 Gi node. The largest free memory block anywhere is roughly 1.2 Gi on `orin-0`; the Sparks have roughly a gigabyte each (1.10 Gi and 0.90 Gi) because the two vLLM ranks request 94 Gi and are limited to 96 Gi by design. The default router is off by more than an order of magnitude, on every node, simultaneously. It is shrinkable — a one-endpoint EPP does not need 8 Gi — but shrinking it puts the deployment off every configuration llm-d's CI covers, in a cluster with no headroom to absorb being wrong.

The gateway integration is missing too. The `llm-d-router-gateway` chart's `provider.name` accepts `["gke", "istio", "none"]`. This cluster's ingress is Envoy Gateway (`gateway-helm` v1.9.1), which serves the `home-ts`, `private` and `public` GatewayClasses; the `istio` and `istio-remote` GatewayClasses exist as inert CRs with no Istio namespace or pods behind them. Envoy Gateway is not a listed provider, and at the pinned version it cannot be one: the v1.9.1 chart contains **zero occurrences of the string `inference`** — no CRDs, no RBAC for `inference.networking.k8s.io`, no templates. The `inferencepools` CRD is correspondingly absent from the cluster. InferencePool on Envoy is an Envoy *AI* Gateway feature, a separate product installed on top. Both llm-d charts, standalone included, render an `inference.networking.k8s.io/v1` InferencePool, so the Gateway API Inference Extension CRDs are a hard prerequisite either way; what standalone mode buys is that llm-d's own bundled Envoy consumes that InferencePool instead of requiring the cluster gateway to implement it. That is a real path, but it means running a second Envoy data plane beside the one already serving the tailnet.

Credit where it is due on the concern that did *not* survive contact: **llm-d's control plane is genuinely arm64**. `ghcr.io/llm-d/llm-d-router-endpoint-picker:v0.10.0` and `llm-d-router-disagg-sidecar:v0.10.0` both publish `linux/amd64, linux/arm64`, and so do the upstream `vllm/vllm-openai` and `lmsysorg/sglang` images llm-d pins. Architecture is not the blocker here, which is worth recording because it is the blocker for a lot of GPU tooling on these nodes. (The `llm-d-latency-predictor-*` images are simply not published at `v0.10.0`, so predicted-latency scheduling is unavailable regardless.) What *is* a blocker is one level down: `linux/arm64` on the manifest is not `sm_121` in the kernels. llm-d's release component pins `docker.io/vllm/vllm-openai:v0.26.0` and `docker.io/lmsysorg/sglang:v0.5.16.0`, and vLLM's own DGX Spark guidance is that stock builds do not carry GB10 kernels — Spark needs the `cu130-nightly` track, `nvcr.io/nvidia/vllm:26.02-py3+`, or a compatible custom build. The active deployment therefore consumes `ghcr.io/miaai-lab/glm-5.3-flash-2x-dgx-sparks` at its pinned digest; MiaAI-Lab publishes the image with the SM121 sparse-MLA and EXL3 runtime, so there is no in-repo serving-image build to maintain. llm-d's `REPLACE_MODEL_SERVER_IMAGE` component makes the pin overridable, so this is not fatal — but the result is still maintaining llm-d's kustomize overlay tree to drive a scheduler with one endpoint to choose from.

One more thing would need recalibration before any of it meant anything. The `prefix-cache-affinity-filter`'s saturation gate keys off `peakPrefillThroughput`, whose default of `15928` is measured for Qwen3-32B on an H100 80 GB at TP=2. Nothing about that number transfers to a 164 GiB EXL3 MoE on unified LPDDR5X, and llm-d's own guide says to measure your own with `guides/recipes/router/calibration`. That is a benchmarking campaign on the only two GPUs in the cluster, which are fully committed to serving.

The one llm-d idea that would pay off at a single replica is tiered prefix caching — spilling evicted KV blocks out of accelerator memory instead of recomputing them. It is worth investigating *without* llm-d, because the serving layer can expose cache and KV behavior directly while there is only one endpoint. But the DGX Spark blunts the usual version of the win: CPU, GPU, OS, container runtime, model weights and KV cache all share **one 128 GB LPDDR5X pool**, so moving a KV block from "HBM" to "CPU RAM" is a reallocation within the same physical memory, not a spill to a larger cheaper tier. The active vLLM deployment already enables prefix caching; any tiered or offloaded variant must be qualified against its `0.75` GPU budget with CUDA-graph capture disabled and 1M context. That is a serving-profile experiment, not a new control plane.

## Consequences

- Keep serving through the existing chain: the `glm53` Service and the `vllm-ts` LoadBalancer, exposed on the tailnet as `stpetersburg-vllm`, with CLIProxy in front as the stable client-facing ID. Do not introduce an EPP hop between CLIProxy and vLLM while there is one endpoint behind it.
- The next inference change on this cluster should be serving-native prefix/KV-cache tuning, not llm-d. Qualify it against the existing guardrails in `kubernetes/apps/base/ai/ai/inference/README.md` — `--gpu-memory-utilization 0.75` with eager execution and CUDA-graph capture disabled, the 1M context, four sequences, 2048 batched tokens, and DFlash2's seven speculative tokens. Treat it as a new load qualification, not a flag flip.
- `hostNetwork: true` on the LWS leader and worker is load-bearing for the RDMA rail and it constrains any future router. InferencePool selects Pods and reads their endpoints; with host networking those are node IPs, and two model-server replicas on one node would collide on `:8000`. Two TP=1 replicas would land one per Spark and so happen to avoid it; any denser packing, or a third replica, would not. A second replica is a networking change as well as a serving one.
- If Gateway API Inference Extension CRDs are ever installed for an unrelated reason, remember that installing them does **not** make Envoy Gateway serve an InferencePool. The v1.9.1 chart has no RBAC for the API group; an InferencePool would be Accepted by nothing and route nowhere. That failure looks like `NoMatchingParent`-class silence rather than a loud error.
- Do not name a future namespace or Kustomization `ai-router` or anything that collides with the existing `ai-inference` pointer. The pointer's `metadata.name` is the app's identity in this repo, and `tools/app.sh` resolves by it.
- Revisit this decision when there are **at least two model-server replicas**, which is the first point at which prefix-aware routing has a choice to make. State the threshold in replicas, not in GPUs: moving to a checkpoint that fits one GB10 reaches it on today's two accelerators, so this is a serving decision that is available now, not a hardware milestone to wait for. Four accelerators is the separate threshold for prefill/decode disaggregation. Do not revisit it merely to experiment with KV offloading, and do not revisit it on the belief that llm-d federates across sites — it schedules within one cluster's InferencePool, so Ottawa would not be routing into St. Petersburg's Sparks.
- If two replicas are ever wanted, weigh the trade on serving terms rather than infrastructure terms. The current GLM-5.3-Flash EXL3 checkpoint is too large for one GB10, so reaching two replicas requires a different checkpoint or quantization. Two TP=1 replicas of a dense model in the 70B class — roughly 40 GB at NVFP4 per this repo's own quantization table, comfortably inside one GB10 with KV room — would roughly double concurrent capacity, do more compute per token, remove the cross-node TP hop, and give each Spark an independent failure domain, which the current single TP=2 group does not have: either Spark rebooting stops all serving. What it gives up is the 1M context and the MoE's breadth. Measure before believing either direction.

## At two replicas, try affinity before a router

If the cluster ever runs two replicas, the thing to reach for first is not llm-d. Two independent
model servers keep two independent KV caches, so a conversation that lands on the wrong replica loses
its whole prefix and re-prefills from scratch — with the >32K agentic prompts this cluster actually
serves, that is the expensive failure. But the fix for it is affinity, and the bounded upside is worth
seeing plainly: at two endpoints, round-robin is already correct half the time, so perfect prefix-aware
routing recovers the other half. That is real and it is not the 3× figure llm-d reports from four- and
sixteen-replica fleets.

Envoy Gateway already does this, on the ingress that is deployed today. `BackendTrafficPolicy` supports
`loadBalancer.type: ConsistentHash`, whose `ConsistentHashType` enum in the `gateway-helm` v1.9.1 CRD is
`SourceIP`, `Header`, `Headers`, `Cookie` and `QueryParams` — and which is used nowhere in this repo so far. Hashing on a conversation or
session identifier pins a chat to one replica for its lifetime, which is most of what the prefix-cache
affinity filter is for, at the cost of one policy object.

What that does *not* give you is llm-d's load-aware half: consistent hashing is oblivious to queue depth,
so a hot conversation keeps its replica even when the other is idle, and rebalancing on a replica restart
is abrupt rather than graded. Those are the terms on which to judge whether the EPP is worth its cost —
against a working affinity baseline, not against round-robin. Measure the baseline first; it is a
`BackendTrafficPolicy`, not a control plane.

## If it is revisited: the install path

Scope it to St. Petersburg, use the **standalone** router (not the gateway chart), and keep the published MiaAI-Lab SM121 serving image. That combination is what keeps it compatible with both Envoy Gateway and the DGX Spark.

1. Install the Gateway API Inference Extension CRDs. They are a hard prerequisite for both charts. Vendor the release manifest under `kubernetes/apps/base/<ns>/…` rather than running llm-d's `guides/recipes/gateway/install-gateway-crds.sh`, which `kubectl apply`s from GitHub release URLs and defaults to `latest` — an unpinned floating install is not a GitOps input. Pin `GAIE_VERSION` to an explicit tag and commit the rendered YAML.
2. Add a `HelmRepository` for the OCI charts at `clusters/common/flux/repositories/helm/llm-d.yaml` pointing at `oci://ghcr.io/llm-d/charts`, `type: oci`, and list it in that directory's `kustomization.yaml`. Chart tags currently published are `v0.9.0`, `v0.10.0-rc.1` and `v0.10.0`; pin a stable tag, not `v0`, which floats.
3. Create `kubernetes/apps/base/llm-d/llm-d-stpetersburg/` with `namespace.yaml` (keep `kustomize.toolkit.fluxcd.io/prune: disabled`), `helmrelease.yaml` for `llm-d-router-standalone`, and `kustomization.yaml`. Set `router.modelServers.matchLabels` to the label the model-server Pods actually carry, and `router.inferencePool.failureMode: FailOpen` so a router fault degrades to direct routing instead of dropping inference.
4. Override the resources before anything else. The chart's 12 CPU / 16 Gi requests and 32 Gi limits will not schedule on any node in this cluster. Size the EPP and the Envoy sidecar to what a small endpoint set actually needs and place the pod on `orin-0` with a nodeSelector, keeping it off the Sparks entirely — GPU-node memory is the scarce resource and the router does not need a GPU.
5. Keep the model-server image pinned to MiaAI-Lab's published arm64 image and digest, which carries the SM121 sparse-MLA and EXL3 runtime. Do not adopt llm-d's `vllm/vllm-openai:v0.26.0` or `lmsysorg/sglang:v0.5.16.0` pins; the stock images do not carry the required GB10 runtime, and a rollout would fail at CUDA init rather than at render time.
6. Calibrate `peakPrefillThroughput` on this hardware with `guides/recipes/router/calibration` before trusting the saturation gate, and schedule that campaign for a window when the endpoint can be taken out of service. Until it is measured, the filter's default will make saturation decisions using an H100's numbers.
7. Track two version streams together — the charts on `v0.10.x` and the EPP image tag they pin — the same way `tools/check-versions.sh` already couples `CephCluster.spec.cephVersion.image` to `rook-ceph-tools`. If llm-d becomes a permanent component, add it to that check rather than relying on Renovate to move both in one PR.
8. Add the pointer `kubernetes/apps/stpetersburg/llm-d/llm-d.yaml` with `spec.path` to the base and `sourceRef.name: kubernetes-manifests`, list it plus the namespace in that directory's `kustomization.yaml`, then run `tools/gen-inventory.sh`, `tools/check.sh stpetersburg` and `tools/check-diagram.sh`. A routing tier in front of inference is a change in how the system works, so expect the diagram gate to require `docs/diagrams/` and `docs/reference/architecture.md` updates rather than just an inventory line.

Two things to know before trusting the default posture. The EPP terminates and parses request bodies to compute prefix hashes, which puts prompt content inside a component that logs at `v: 2` by default — raise nothing above that without checking what lands in `fluent-bit` and VictoriaLogs. And the standalone router's bundled Envoy is a second data plane with its own version stream (`envoyproxy/envoy:distroless-v1.33.2` at chart v0.10.0), independent of the `gateway-helm` version Renovate tracks for the ingress; it will not move when Envoy Gateway does.
