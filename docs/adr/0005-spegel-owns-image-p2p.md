# Spegel owns image P2P; model weights go through Garage, not Dragonfly

Dragonfly ([d7y.io](https://d7y.io/docs/)) is a CNCF-graduated peer-to-peer distribution system for container images and large files, and it is deliberately not deployed here. Peer-to-peer image distribution is Spegel's job on all three clusters, and Dragonfly's node-configuration agent is structurally incompatible with Talos besides.

The blocker is `dfinit`, the init container that wires containerd up. Its fallback path writes `/etc/containerd/config.toml` — a file that does not exist on Talos, under a directory Talos mounts read-only — and then runs `nsenter -t 1 -m -- systemctl restart containerd.service`, on a system whose PID 1 is `machined` and which ships no `systemctl` at all. The chart's hostPath is `dir(configPath)`, i.e. `/etc/containerd`, not the `/etc/cri/conf.d/hosts` that Talos actually sets `config_path` to. There is no published precedent for Dragonfly on Talos anywhere: no mention of Talos in any `dragonflyoss` repository, and no mention of Dragonfly in `siderolabs/talos`. Spegel, by contrast, is documented for Talos by both its own project and Sidero Labs. The one practitioner write-up that tried Dragonfly on managed Kubernetes ([knechtions.com](https://knechtions.com/improving-container-image-pull/), March 2026) got stuck on exactly this — containerd restarting out from under the init container that requested it — and gave up after three days.

A Talos-shaped route does exist, because the `hosts.toml` that `dfinit` would generate is entirely static: run in lightweight mode with `dfinit.enable: false` and `restartContainerRuntime: false`, and express the mirror declaratively in machine config. But that route collides with the incumbent. Both Spegel and Dragonfly would be writing mirror config into `/etc/cri/conf.d/hosts`, and Talos's own `syncHosts()` reconciler does a `RemoveAll` over directories under that tree which aren't derived from `RegistryMirrorConfig` — so introducing a `RegistryMirrorConfig` to point at Dragonfly is liable to prune Spegel's files and silently stop mirroring until its pods restart. One of the two has to own containerd; they cannot share it.

On proportion, the chart's own defaults are the argument. Chart 1.8.2 requests **8 CPU and 16Gi for the seed client, at three replicas** — 24 CPU, 48Gi and 300Gi of volumes before a single per-node peer — against Spegel's entire footprint of 128Mi per node with no CPU request and no storage at all, because Spegel re-serves containerd's existing content store rather than keeping a cache of its own. The chart also pins Manager and Scheduler to `v2.5.2-rc.0`, a release candidate, while stable is v2.5.1. Two independent version streams have to be tracked and moved together — the Go server components on 2.5.x and the Rust client on 1.5.x — with no published compatibility matrix and a maintainer confirming the Go and Rust clients are wire-incompatible; that is the same class of constraint `tools/check-versions.sh` already enforces for `CephCluster` against `rook-ceph-tools`. Note that the frequently repeated claim that Dragonfly needs MySQL and Redis is now out of date: as of July 2026 the chart defaults `manager.enable`, `mysql.enable` and `redis.enable` all to false, and the documented recommendation for small clusters is a lightweight Scheduler + Seed Client + Client deployment with no database at all. The database is the price of the web console, Open API and API-driven preheating, not of P2P itself.

The one real gap Dragonfly would have closed is that model weights are not an image problem and nothing here addresses them. St. Petersburg serves `RadixArk/Qwen3.8-Flash-Next-NVFP4` (~135 GB) as a two-member LeaderWorkerSet across `spark-0` and `spark-1`, and each member's init container runs its own `snapshot_download` against the pinned `HF_REVISION` into its own 200 GiB volume. The cause is storage, not networking: the cluster's only storage class is `local-path`, which is ReadWriteOnce, so there is no shared volume for two nodes to read one copy from. At the ~390 Mbps per-node ingest observed, the duplicate copy costs roughly fifty minutes of wall clock and 135 GB of egress every time the revision moves.

That gap is closed with Garage instead, which already runs on St. Petersburg as two gateways over three local storage nodes and is already one of the seven substitution sources every pointer inherits: `download-and-validate.sh` tries a Garage bucket first and falls back to HuggingFace, writing back on a miss, so the first node to start pays the WAN cost once and the second reads over the LAN. No containerd change, no new control plane, no release-candidate images. The decisive point is that Dragonfly would buy nothing more here — peer-to-peer accelerates fan-out across *many* nodes, and at two nodes it saves exactly one copy, which is exactly what a shared bucket saves.

Note also that "dragonfly" is thoroughly taken in this tree. Seven `dragonflydb.io` CRs across `media`, `zot`, `buzz` and `immich` are DragonflyDB, the Redis-compatible datastore, with a `dragonfly-operator-system` namespace on Ottawa and Robbinsdale. One of them backs zot's cache.

## Consequences

- `tools/refs.sh dragonfly` finds DragonflyDB, seven times over. If d7y.io Dragonfly is ever adopted, its namespace and Flux Kustomization must be named something like `d7y-system`; naming it `dragonfly` would make every future grep ambiguous against components that are load-bearing for the registry and for two media stacks.
- Spegel's containerd prerequisites are load-bearing and easy to break silently. `discard_unpacked_layers = false` must stay in every cluster's `20-customization.part` — Talos defaults it to true, and removing the patch leaves Spegel running and advertising content it can no longer serve. Dragonfly would not need that setting, since it keeps its own cache rather than reading containerd's store, but it cannot be removed while Spegel is deployed.
- Do not introduce a Talos `RegistryMirrorConfig` on these clusters without accounting for Spegel. Talos prunes files under `/etc/cri/conf.d/hosts` that no longer derive from that config, which can disable mirroring until the Spegel DaemonSet restarts. `spegel.prependExisting: true` exists for this coexistence case.
- Spegel's startup no longer validates the containerd registry config, so a wrong `containerdRegistryConfigPath` fails silently rather than loudly. Confirm mirroring is actually working via `Last Mirror Success` on Spegel's `/debug/web`, not by pod readiness.
- Because no cluster sets Talos-level registry mirrors, the first pull of a new tag always goes to source, and two nodes starting the same rollout simultaneously both go to source — Spegel has nothing to share yet. This is inherent to Spegel, which can only serve what some node already has, and is not what Dragonfly would fix either.
- The zot pull-through cache on Ottawa is built, running with `onDemand` sync from `ghcr.io` onto Garage S3, and unused: no manifest in the repo pulls images through it. Chaining it via `spegel.additionalMirrorTargets` is the cheap way to cover the cold-pull path, and is the move to make before considering any new caching tier.
- Revisit this decision if the GPU fleet grows well past a handful of nodes, where seed peers and back-to-source collapse start to pay for themselves, or if weights move into OCI artifacts and Nydus lazy loading becomes viable on Talos. Do **not** revisit it on the belief that Dragonfly distributes across sites: a single Manager manages multiple scheduler clusters, but peers can only transmit data within their own Dragonfly cluster, so multi-cluster buys centralized management and preheat orchestration, not Ottawa peers pulling bytes from St. Petersburg.

## If it is revisited: the install path

Scope it to St. Petersburg, in lightweight mode, and never point it at containerd — that is what keeps it Talos-compatible and keeps Spegel intact.

1. Add a `HelmRepository` at `clusters/common/flux/repositories/helm/d7y.yaml` for `https://dragonflyoss.github.io/helm-charts` and list it in that directory's `kustomization.yaml`. Note this is a classic HTTP chart repo, not OCI — unlike Spegel, which this repo consumes as `type: oci`.
2. Create `kubernetes/apps/base/d7y-system/d7y/` with `namespace.yaml` (keeping `kustomize.toolkit.fluxcd.io/prune: disabled` and `pod-security.kubernetes.io/enforce: privileged`, as `kubernetes/apps/ottawa/spegel/namespace.yaml` already does), `helmrelease.yaml`, and `kustomization.yaml`.
3. In the HelmRelease values, keep `manager.enable`, `mysql.enable` and `redis.enable` false; set `dfinit.enable: false` and `restartContainerRuntime: false`, which removes both privileged init containers and every host mutation; drop `scheduler.replicas` and `seedClient.replicas` to 1; and override the seed client's 8 CPU / 16Gi requests to something a three-node cluster can actually schedule. Override the Manager and Scheduler image tags off `v2.5.2-rc.0` if they are ever enabled.
4. Bound the cache explicitly. The client's storage is a default `emptyDir` with no `sizeLimit`, and its GC thresholds are percentages of the whole filesystem, so on Talos it will grow against `/var` — shared with containerd's image store and kubelet — until 80–90% full before GC engages. Set `client.config.storage.diskThreshold`, or give it a dedicated volume.
5. Fetch weights with `dfget hf://RadixArk/Qwen3.8-Flash-Next-NVFP4 --recursive --hf-revision <rev> --hf-token …`, which is native HuggingFace support needing no proxy rules and no TLS interception. Use the injector webhook (`injector.enable: true`, requires cert-manager) to place `dfget` and the dfdaemon socket into the pod rather than rebuilding the serving image. Reach for the HTTP proxy on port 4001 with `proxy.caCert`/`proxy.caKey` only if `hf://` proves insufficient — that path does mint per-host certs and does intercept traffic.
6. Add the pointer `kubernetes/apps/stpetersburg/d7y-system/d7y.yaml` (`spec.path` to the base, `sourceRef.name: kubernetes-manifests`) and list it plus the namespace in that directory's `kustomization.yaml`.
7. Run `tools/gen-inventory.sh`, then `tools/check.sh stpetersburg` and `tools/check-diagram.sh`. A new caching tier is one of the few changes that genuinely belongs in `docs/diagrams/`, so expect the diagram gate to have an opinion.

Two things to know before trusting the default posture: the proxy on port 4001 ships with `basicAuth` commented out and peer mTLS commented out, so with `hostNetwork: true` that is an unauthenticated forward proxy on every node's host network — which matters on a fabric where pod and node CIDRs are reachable over the tailnet. And uninstalling does not undo host mutations; upstream's position is that `dfinit` will not remove what it wrote. Keeping `dfinit.enable: false` avoids both concerns entirely.
